# SharkTooth 實測：接收與分析程式

用三塊 B-L475E-IOT01A，在 PC 上重現 SharkTooth 論文（Landra et al., IEEE IoT-J 2025）的 **Fig. 6**（延遲修正）和 **Fig. 9**（同步前後的波形）。

| 程式 | 做什麼 | 什麼時候用 |
| --- | --- | --- |
| `st_receiver.py` | 用藍牙同時連 1～3 塊板子，每收到一包就打 PC 時間 t_C，存成一個實驗資料夾 | 錄資料 |
| `st_rawplot.py` | 只畫原始的 δT = t_C − t_P，不跑 SharkTooth | 錄完先看資料本身正不正常 |
| `st_analyze.py` | 跑 SharkTooth，畫論文樣式的 Fig. 6、Fig. 9，並印出同步誤差摘要 | 出結果 |

三支程式放在同一個資料夾（`st_rawplot.py` 會用到 `st_analyze.py` 裡的函式）。

### 檔案與資料夾的分層

```
sharktooth_pc/
├── README.md
├── st_receiver.py
├── st_rawplot.py
├── st_analyze.py
└── runs/
    ├── 20261101_154817/
    │   ├── packets.csv
    │   ├── events.csv
    │   ├── meta.json
    │   ├── raw_NODE_A.png
    │   ├── raw_NODE_B.png
    │   ├── raw_NODE_C.png
    │   ├── unpredictable_delay_correction_NODE_A.png
    │   ├── unpredictable_delay_correction_NODE_B.png
    │   ├── unpredictable_delay_correction_NODE_C.png
    │   ├── unpredictable_delay_correction_NODE_A_annotated.png
    │   ├── unpredictable_delay_correction_NODE_A_paper.png
    │   ├── unpredictable_delay_correction_NODE_A_tilt150.png
    │   └── synchronization_example.png
    └── 20261101_163000/
        └── …
```

- **原始資料只有三個檔**：`packets.csv`、`events.csv`、`meta.json`。圖都可以從它們重新畫出來，所以要備份、要給同學重現，留這三個檔就夠了。
- **圖會畫在資料所在的同一個資料夾**，重跑會直接覆蓋同名的圖；用 `--paper` 或其他 `--tilt` 時檔名會加後綴，不會蓋掉預設版。
- **錄失敗的資料夾**（例如搜尋不到板子、沒收到任何封包）裡面只有空的 CSV，程式結束時會提示可以刪掉。
- 韌體（CubeIDE 的 `sharktooth` 專案）是另一個資料夾，和這裡無關。

## 1. 需要的東西

**硬體**

- 1～3 塊 B-L475E-IOT01A，燒好 `sharktooth` 韌體（Build Configuration 選 Node A / B / C）
- 函數產生器（或示波器內建的訊號產生器）
- 電腦內建藍牙（或 USB 藍牙接收器）
- 三用電表（接線前檢查電壓用）

**軟體**

- Python 3.10 以上
- 套件：

```
pip install bleak numpy matplotlib
```

## 2. 訊號設定（對照論文）

| 項目 | 論文 | 這個實驗 | 說明 |
| --- | --- | --- | --- |
| 參考訊號 | 5 Hz 正弦 | **5 Hz 正弦** | 一樣 |
| 輸入方式 | 兩個反相正弦接到 AFE 的差動輸入，放大後輸出 1 Vpp | **一個正弦直接接 ADC** | 板子上沒有 AFE，直接給 ADC 能吃的電壓 |
| 進 ADC 的訊號 | 1 Vpp | **1 Vpp，offset +1.25～1.65 V** | 只要整個波形落在 ADC 的 0～3.3 V 內、上下留一點餘裕就好，不必剛好置中 |
| 取樣率 | 50 Hz | 50 Hz（TIM6） | 一樣 |
| 每包樣本數 | 5（每 100 ms 一包） | 5 | 一樣 |
| 封包大小 | 17 / 127 / 244 B | 20 B | BlueNRG-MS 上限 20 B，對應論文的 17 B 組 |
| 節點數 | 2～12 | 1～3 | 對應論文 Table II 的 2、4 節點附近 |
| 每次錄多久 | 1 小時 × 20 次 | 先 5～30 分鐘，再 1 小時 | 見第 5 節 |

### 函數產生器設定

| 項目 | 設定 |
| --- | --- |
| 波形 | Sine |
| 頻率 | 5 Hz |
| 振幅 | 1 Vpp |
| Offset | +1.65 V；產生器最多只能給 +1.25 V 時就用 +1.25 V（訊號 0.75～1.75 V，一樣可以） |
| 輸出負載 | **High-Z**（重要：設成 50 Ω 時，接到 ADC 的實際電壓會是面板數字的兩倍。很多產生器在 50 Ω 模式下 offset 上限只有 High-Z 的一半，所以如果 offset 最多只能設 1.25 V，先確認是不是停在 50 Ω 模式） |

## 3. 接線

| 函數產生器 | 接到每一塊板子 | 位置 |
| --- | --- | --- |
| **正**（紅夾子 / BNC 中心） | **A0**（PC5） | Arduino 類比排針，絲印 `A0` |
| **負**（黑夾子 / BNC 外殼） | **GND** | Arduino 電源排針，絲印 `GND` |

三塊板子並聯：

```
產生器 正 ──┬── NODE_A 的 A0
            ├── NODE_B 的 A0
            └── NODE_C 的 A0

產生器 負 ──┬── NODE_A 的 GND
            ├── NODE_B 的 GND
            └── NODE_C 的 GND
```

板子用 USB 接電腦供電，**不要**接板子的 3V3 或 5V 腳。

### 接線順序（每次都照做）

1. 產生器**關閉輸出**，照上表設定好。
2. 三用電表 DC 檔量產生器「負」和板子 GND 之間，應小於 1 V；AC 檔也量一次（第 9 節有說明）。
3. **先接 GND**，再接 A0。
4. 開輸出，三用電表量 A0 對 GND，應該約等於你設的 offset（1.25～1.65 V）。有示波器的話，直接看波形最高點不超過約 2.2 V、最低點不低於 0 V。
5. 開序列埠看板子印的 `adc ...`：offset 1.65 V 時約在 1430～2670 之間跳動，offset 1.25 V 時約在 930～2170。

拆線順序相反：關輸出 → 拆 A0 → 拆 GND。

## 4. 實驗前的電腦設定

電腦太忙時，t_C 會被延後，δT 會多出往上跳的點。

- 插電，電源模式設「最佳效能」，關閉睡眠與螢幕關閉
- **不要用藍牙耳機或藍牙滑鼠**（會跟板子搶同一個藍牙晶片）
- 不要視訊、下載大檔、跑防毒掃描
- 手機 App 不要連著板子（板子一次只能連一個裝置）

## 5. 快速開始

### 每次錄之前

1. 三塊板子都按一次黑色 **RESET** 鍵（找不到就拔插 USB）。
2. 每塊板子的序列埠都要印出 `advertising: 0x00`，而且 `adc ...` 的值在正常範圍（第 3 節第 5 步）。
3. Windows「設定 → 藍牙與裝置」裡如果有 NODE_A / B / C，先「移除裝置」；手機 App 關掉。

### 完整流程（三塊板子）

```
# 1. 錄資料（30 分鐘）
python st_receiver.py --names NODE_A NODE_B NODE_C --minutes 30 --note "請求 CI 30 ms; 5 Hz 1 Vpp offset 1.65 V High-Z"

# 2. 先看原始資料
python st_rawplot.py runs/20261101_160000

# 3. 跑 SharkTooth、畫 Fig. 6 和 Fig. 9
python st_analyze.py runs/20261101_160000 --ci 0.030
```

`runs/...` 換成接收程式結束時印出的資料夾名稱。`--ci` 換成實際的 connection interval（見第 8 節「實際的 CI 怎麼知道」）。

### 只用一塊板子

```
python st_receiver.py --names NODE_A --minutes 5 --note "5 Hz 1 Vpp"
python st_analyze.py runs/20261101_153000 --ci 0.030
```

只有一塊板子時，Fig. 9 只會有一條線，沒有比較的意義，看 Fig. 6 就好。

**同時錄三塊和一次錄一塊，Fig. 6 不會完全一樣**：α 幾乎相同（看晶振），β 每次都不同，藍點的分布（ε）在三塊同時連線時可能比較亂。要做 Fig. 9，就用三塊一起錄的那一組畫 Fig. 6。

### 常用指令一覽

| 想做什麼 | 指令 |
| --- | --- |
| 三塊各畫一張 Fig. 6 + Fig. 9 | `python st_analyze.py runs/<資料夾> --ci 0.030` |
| 只畫 NODE_B 的 Fig. 6 | `python st_analyze.py runs/<資料夾> --ci 0.030 --fig6-node NODE_B` |
| 多輸出一張加註版 Fig. 6（標 α、β、帶寬） | `python st_analyze.py runs/<資料夾> --ci 0.030 --annotate` |
| 完全照論文的算法（不加預傾斜） | `python st_analyze.py runs/<資料夾> --ci 0.030 --paper` |
| 完全照論文的條件（含 30.51 µs tick 常數） | `python st_analyze.py runs/<資料夾> --ci 0.030 --paper --tick-us 30.51` |
| Fig. 9 改畫第 600 秒、畫 2 秒 | `python st_analyze.py runs/<資料夾> --ci 0.030 --fig9-at 600 --fig9-span 2` |
| Fig. 9 不要圖例（和論文一樣） | `python st_analyze.py runs/<資料夾> --ci 0.030 --no-legend` |
| 原始資料只看前 140 秒 | `python st_rawplot.py runs/<資料夾> --span 140` |

### 對照論文 Table II

論文每組設定錄 1 小時、重複 20 次，再分成 6 段 × 10 分鐘看誤差怎麼收斂。要做類似的比較，至少錄 1 小時：


## 6. `st_receiver.py`

### 參數

| 參數 | 預設 | 說明 |
| --- | --- | --- |
| `--names` | `NODE_A` | 要連的節點名稱，可以列多個 |
| `--minutes` | 10 | 錄多久，中途可以按 Ctrl+C 提早結束（資料會存好） |
| `--outdir` | `runs` | 實驗資料夾放在哪裡 |
| `--note` | 空白 | 附註，例如訊號設定、擺放位置，會寫進 `meta.json` |

### 執行時的畫面

```
[  2.5 min] NODE_A: 10.0/s  NODE_B: 10.0/s  NODE_C:  9.8/s   迴圈延遲最大   1.2 ms
```

- **時間**：每 5 秒印一行，但時間以 0.1 分鐘（6 秒）顯示，所以偶爾兩行會是同一個數字（例如兩行都是 4.3 min），那是相差 5 秒的兩筆統計，不是重複。
- **每秒幾包**：正常約 10 包/秒（每 100 ms 一包）。明顯偏低代表有掉包或連線不穩。
- **迴圈延遲最大**：這 5 秒內程式最多被卡住多久。超過 5 ms 會標出「← 電腦卡住過」，表示這段時間的 t_C 可能被延後。偶爾一兩次 5～15 ms 沒關係，常常出現才要處理（第 4 節）。

### 輸出：`runs/<日期_時間>/`

| 檔案 | 內容 |
| --- | --- |
| `packets.csv` | 每包一列：`node, t_C, pkt_id, tP_ticks, fl_ticks, n, s0..s4, node_byte, qdrop, raw_hex` |
| `events.csv` | 連線、notify、斷線的時間，以及每 5 秒的封包率和迴圈延遲 |
| `meta.json` | 參數、板子藍牙位址、作業系統、Python / bleak 版本、開始時間、附註、總封包數 |

保留整個資料夾，就能用 `st_analyze.py` 重跑分析。`raw_hex` 是原始的 20 bytes，之後封包格式改了也能重新解析。

**t_C 的定義**：`time.perf_counter()` 減去「所有板子都連好、送出 notify 之前」那一刻，單位是秒，和論文一樣。所以 δT 的起點差（β）只剩 notify 傳到板子的時間，約零點幾秒。（2026-11-01b 以前的版本是從程式開始算，β 會多出搜尋 + 連線的好幾秒。）收到封包時第一件事就是打 t_C；寫硬碟交給背景執行緒，每秒一次，不會拖慢 t_C。

### 封包格式（20 bytes，little-endian，和韌體一致）

| byte | 欄位 | 說明 |
| --- | --- | --- |
| 0 | `pkt_id` | 封包編號（mod 256），用來算掉了幾包 |
| 1–4 | `tP_ticks` | 這包**最後一個樣本**的時間戳，LSE tick（1 tick = 1/32768 s），從 notify 打開起算 |
| 5–6 | `fl_ticks` | 第一個到最後一個樣本的時間差（tick），用來算包內每個樣本的時間 |
| 7 | `n` | 樣本數（5） |
| 8–17 | `s0`～`s4` | 5 個 ADC 值（12 位元，0～4095） |
| 18 | `node_byte` | 節點代號 `'A'` / `'B'` / `'C'` |
| 19 | `qdrop` | 節點端因為落後太多而跳過的封包數（mod 256） |

## 7. `st_rawplot.py`（看原始資料）

不跑任何算法，每一包畫一個點：δT = t_C − t_P。用來在分析之前確認資料本身正常：有沒有斷掉、帶子多厚、重傳多不多、斜率往哪邊。

```
python st_rawplot.py runs/<資料夾>
python st_rawplot.py runs/<資料夾> --span 140      # 只畫前 140 秒
```

| 參數 | 預設 | 說明 |
| --- | --- | --- |
| `data` | （必填） | 實驗資料夾 |
| `--span` | 全部 | 只畫前幾秒 |

**輸出**：每塊板子一張 `raw_<節點>.png`

- 上圖：原始 δT（秒），完全沒處理。整體高度約等於 β（兩個時鐘零點的差），不是傳輸延遲。
- 下圖：δT 減掉最小值（ms），看延遲的分布：帶子厚度 ≈ 1 個 CI，上方零星的點是重傳。

**終端機**會印出每塊板子：第一包的 t_P、t_C、δT，連線與 notify 打開的時間，延遲的中位數、95% 範圍、最大值。

## 8. `st_analyze.py`（出結果）

### 參數

| 參數 | 預設 | 說明 |
| --- | --- | --- |
| `data` | （必填） | 實驗資料夾，或一個 CSV 檔 |
| `--ci` | 0.030 | **實際的** connection interval（秒）。SharkTooth 的 Eq. 10 會用到 |
| `--tilt` | 100 | 預傾斜（ppm）。先在 δT 加上已知的 +100 ppm 斜率再跑算法，算完扣回。0 = 不加 |
| `--paper` | 關 | 完全照論文：不加預傾斜（等於 `--tilt 0`），30 秒穩定期內 α = β = 0。圖檔名後面加 `_paper` |
| `--tick-us` | 30.5176 | 每個 tick 當成幾 µs。填 `30.51` = 用論文韌體的換算常數（等於人為加上約 +248 ppm） |
| `--fig6-node` | 每個節點各一張 | Fig. 6 只畫哪個節點，例如 `NODE_B` |
| `--fig6-span` | 140 | Fig. 6 畫前幾秒（論文約 140 秒） |
| `--annotate` | 關 | 多輸出一張中文加註版 Fig. 6：標出 α、β、開頭突降、帶寬 |
| `--fig9-at` | 最短資料長度的 80% | Fig. 9 從哪個 t_P（秒）開始畫。要選後段，SharkTooth 才收斂 |
| `--fig9-span` | 1.0 | Fig. 9 畫幾秒（論文約 1 秒，5 個週期） |
| `--no-legend` | 關（有圖例） | Fig. 9 不畫「哪條線是哪塊板子」的圖例（和論文一樣） |

### 為什麼預設要加預傾斜

論文的算法隱含「δT 的下緣往上斜」（α ≥ 0）的前提。板子晶振比電腦快時 α 是負的，下緣一直往下走，每個新低點都會變成新的樞紐點，斜率不斷歸零，紅線收斂不了。

加上已知的 +100 ppm，下緣變成往上斜，算法就能正常運作；算完把 100 ppm 扣回去，α、β 還是板子真正的值。每一包的延遲 ε 不會被改到。預傾斜在 60～250 ppm 之間，結果幾乎一樣（α 差 \< 1 ppm，β 差 \< 0.3 ms）；太大（400 ppm 以上）會開始偏掉。論文的板子因為 30.51 µs tick 常數，其實也被加了約 +248 ppm。

### 實際的 CI 怎麼知道

連上之後，板子的序列埠會印：

```
connected, interval = 24 x 1.25 ms
conn update, interval = 24 x 1.25 ms
```

以**最後一行**為準：24 × 1.25 ms = 30 ms，所以填 `--ci 0.030`。三塊板子的 CI 可能不一樣，填最常見的那個。

這兩行只會在**板子的序列埠**（CubeIDE 的 Console）出現，而且只在連上的那一刻印一次，之後會被每秒的 `adc ...` 洗上去。可以在 Console 按 Ctrl+F 搜尋 `interval`。

找不到也沒關係：`st_analyze.py` 的摘要會**從封包到達的時間推估 CI**（封包只能在 connection event 送出，所以到達時間會排成間隔 = CI 的格子）。推估值和 `--ci` 不同時會提醒你改用哪個值。

### 輸出（放在實驗資料夾裡）

| 檔案 | 內容 |
| --- | --- |
| `unpredictable_delay_correction_<節點>.png` | 論文 Fig. 6：δT（藍點）、SharkTooth 估的下緣 δT\*（紅線）、最後一個樞紐點（綠色星號）。標題第二行是哪一塊板子，圖下方是這塊板子錄完時的 α、β |
| `unpredictable_delay_correction_<節點>_annotated.png` | 加了 `--annotate` 才有：中文加註版 |
| `synchronization_example.png` | 論文 Fig. 9：上：各節點用自己的 t_P（未同步）；下：用 t̂\_S（已同步）。最上方的圖例標出哪個顏色是哪塊板子 |

- 檔名後面的 `_paper` / `_tilt<數字>`：用了 `--paper` 或非預設的 `--tilt` 時才會加，不會蓋掉預設版的圖，方便放在一起比較。
- 圖下方的 α、β：δ̂T = α·t_P + β，已扣掉預傾斜。用 `--paper` 且錄完時剛好在 30 秒穩定期內，會顯示 not available。
- 圖的尺寸是 IEEE 單欄寬（3.5 吋），字型用 Times，只輸出 PNG（300 dpi），可以直接放進報告或投影片。

### 兩張圖怎麼算出來的

**Fig. 6**：每收到一包算 δT = t_C − t_P（藍點）。δT = α·t_P + β + ε，而延遲 ε ≥ 0，所以藍點雲的下緣就是 α·t_P + β。算法用最低點（樞紐點）當起點、用門檻線擋掉延遲大的點、用剩下的點修正斜率，畫出紅線 δT\*（論文 Algorithm 2）；樞紐點穩定 30 秒後，對紅線做最小平方擬合得到 α、β（Algorithm 1）。

**Fig. 9**：每個樣本的時間由封包往回推：t = t_P − (4 − k)·fl / 4。上圖直接用各自的 t_P 畫，三塊板子零點、快慢都不同，所以錯開。下圖用 t̂\_S = t_P + α·t_P + β 換到電腦的時間軸，同一瞬間的樣本落在同一點，所以對齊。用的是每一包當下的 α、β（和即時系統一樣）。

## 9. 疑難排解

| 現象 | 可能原因 | 怎麼辦 |
| --- | --- | --- |
| `找不到 NODE_A` | 板子沒在廣播：還掛著上一次的連線、手機連著它、名字打錯 | 按 RESET（或拔插 USB），看序列埠有沒有 `advertising: 0x00`；Windows 藍牙設定裡移除該裝置；關手機 App |
| 序列埠視窗全空白 | 三個視窗開到同一個連線、拔插後 COM 號碼變了、板子停在 Debug 模式 | 裝置管理員確認每塊的 COM 號碼並重新連線；Debug 時按 Resume 或 Terminate；按 RESET 應該馬上印出 `lptim start` 等開機訊息 |
| 三塊板子序列埠印的 adc 值都不一樣 | 正常：三塊取樣的時刻不同，拍到弦波的不同位置 | 不用處理，Fig. 9 下圖對齊就代表沒問題 |
| Fig. 9 某一條線的振幅、中心明顯比其他條小 | 那塊板子的 A0 或 GND 接觸不良 | 把它和正常的板子交換整組接線，看問題跟著線還是跟著板子；三用電表量 A0 對 GND 應接近 1.65 V |
| 每秒包數遠低於 10 | 干擾、距離太遠、電腦在忙 | 靠近一點、關藍牙耳機、看「迴圈延遲」 |
| 「迴圈延遲」常常超過 5 ms | 電腦在忙 | 照第 4 節設定，關掉其他程式 |
| 摘要說 `t_P 倒退` | 錄的時候板子重開機，或 notify 被關掉再打開 | 程式只會用最長的一段；最好重錄 |
| `δT 斜率` 是負的，Fig. 6 的紅線一直重來 | 用了 `--tilt 0` 或 `--paper` | 用預設的 `--tilt 100` |
| Fig. 6 藍點排成整齊的橫條紋（另一塊是散開的點雲） | 正常：封包間隔和 CI 剛好接近簡單比例（例如 99 ms : 30 ms ≈ 10 包繞回原位） | 不用處理，下緣一樣清楚 |
| Fig. 9 下圖沒對齊 | `--fig9-at` 選在太前面，SharkTooth 還沒收斂 | 選錄到後半段的時間 |
| ADC 值一直是 0 或 4095 | A0 或 GND 沒接好，或電壓超出範圍 | 回到第 3 節重新檢查 |
| 三用電表量產生器負和板子 GND 有幾十 V 交流 | 筆電用兩孔變壓器，地浮在交流電上 | 電流很小，先接 GND 就安全；更好的做法是筆電改用電池或三孔變壓器 |

## 10. 和論文不同的地方

- **沒有 AFE**：訊號直接進 ADC，所以沒有論文那種各節點約 0.1 ms 的類比延遲差，殘餘延遲可能比論文小。
- **Central 是電腦內建藍牙**，不是 nRF52840 dongle：CI 和各節點錯開的時間由作業系統決定，不能指定。
- **封包只有 20 B**：只能對照論文 17 B 那一組，看不到「封包越長、誤差越大」的趨勢。
- **時間戳傳原始 tick**：在 PC 上用精確的 32768 換算，所以不會有論文那個 +245 ppm 的斜率。
- **預設加了預傾斜**（`--tilt 100`）：論文沒有，用來處理晶振漂移為負的情況（第 8 節）。要完全照論文用 `--paper`。
- **穩定期內保留上一次的 α、β**：論文在換樞紐點後的 30 秒內令 α = β = 0；程式預設延用上一次的值（只影響摘要的「有輸出 %」）。`--paper` 會改回論文的做法。
